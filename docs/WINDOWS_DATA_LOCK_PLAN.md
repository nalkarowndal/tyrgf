# Windows 데이터 잠금 전환

## 원인과 범위

기존 잠금은 정규화한 데이터 폴더의 SHA256을 TCP 20000~49999 포트 하나로 매핑한다. 같은 데이터 폴더의 앱·백업·복원은 같은 포트를 독점하고 종료 시 OS가 해제한다. 하지만 Windows 제외 포트와 겹치면 앱이 없어도 EACCES로 시작할 수 없다. 7522c3f 진단에서 512개 중 3개가 제외 범위와 일치했다.

실패 후 다른 포트를 고르는 방식은 쓰지 않는다. EACCES는 다른 프로세스의 독점 바인딩에서도 발생할 수 있어 잠금 우회로 이어진다.

## 변경 설계

- Windows: 정규화한 데이터 폴더의 SHA256 전체를 사용하는 `\\.\pipe\aura-data-v2-<64자리 해시>` 리스너를 잠금으로 사용한다. Node 24.19.0의 libuv는 첫 인스턴스 생성 시 `FILE_FLAG_FIRST_PIPE_INSTANCE`를 사용하며 중복 바인딩을 거절한다.
- Linux/macOS: 기존 TCP 잠금 규약을 유지한다. Windows 예약 포트 문제의 수정 범위를 넘어 플랫폼별 잠금을 바꾸지 않는다.
- 모든 진입점이 동일한 `acquireDataLock`을 사용한다. 잠금 실패 시 데이터 접근을 중단한다. 임의 이름·포트 재시도나 파일 삭제로 잠금을 해제하지 않는다.
- 파이프 연결이 들어오면 즉시 닫으며 데이터를 주고받지 않는다. OS 핸들이 종료되면 잠금이 해제된다. 다른 사용자에게 파이프 읽기/쓰기 권한을 추가하지 않는다.
- CLI는 허용한 OS 오류 코드와 `Windows 데이터 잠금` 유형만 표시한다. 경로, 해시 이름, stack, 암호는 진단에 출력하지 않는다.

## 업데이트 조건

이것은 Windows 잠금 **규약 변경**이다. TCP를 쓰는 이전 후보와 파이프를 쓰는 새 후보는 서로의 잠금을 공유하지 않는다. 혼합 실행 차단을 보장하지 않는다.

업데이트 전 기존 앱 서버·백업·복원을 모두 종료해야 한다. 브라우저만 닫아서는 서버가 종료되지 않는다. 이후 설치본과 portable을 포함한 모든 실행/백업 도구를 새 후보로 교체하고 이전 후보는 같은 데이터에 다시 실행하지 않는다. 기존 DB와 백업 형식은 바꾸지 않는다. 현재는 정식 출시 이전 후보이며 이 조건을 배포 문서와 설치 안내에 표시한다.

## 검증

1. Windows 제외 범위와 실제 EACCES를 동시에 확인하는 경로를 찾고, 기존 코드에서 잠금 획득 실패를 재현한다. OS 설정을 변경하지 않는다.
2. 같은 검사에서 새 코드의 획득·중복 차단·해제 후 재획득을 확인한다.
3. 독립 프로세스 4개의 경쟁에서 1개만 성공해야 한다. 정상 종료와 강제 종료 뒤 다시 획득할 수 있어야 한다.
4. 별칭/junction·대소문자 경로는 동일 잠금으로 해석하고, 다른 데이터 폴더는 독립 실행한다.
5. 앱과 CLI의 충돌 거절·진단 비밀 비노출, 실제 Windows 배포 번들·백업/복원·설치 수명주기를 재검증한다.
6. 표본 512개 검사는 별도 관측이다. 모두 성공하더라도 모든 Windows 환경의 가용성을 보장하는 통계로 표시하지 않는다.
